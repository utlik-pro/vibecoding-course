Что такое бэкенд? (простыми словами)

Бэкенд — это «невидимая часть» сайта, которая считает, сохраняет и проверяет данные. Разберёмся на примере Money Tracker — простого приложения для учёта личных финансов.

📚 Как устроен весь этот модуль

Мы не учим теорию ради теории. Подход модуля 6 — другой:

  1. В этом уроке вы возьмёте готовый PRD (описание проекта) для Money Tracker и скормите его task-master из модуля 5. Получится 8–12 конкретных задач: «настрой Supabase», «сделай таблицу», «напиши Server Action для добавления»…
  2. Уроки 6.2–6.9 — это поэтапная реализация этих задач. На каждом этапе:
    • Cursor или Claude Code генерирует код по задаче из Task Master
    • Мы останавливаемся и разбираем: «вот это — API», «вот это — SQL», «вот это — Server Action»
    • Запускаем код, видим результат — переходим к следующей задаче
  3. В конце у вас работающее приложение + понимание, что такое каждая его часть.
Почему так лучше для нулевиков: когда вы изучаете бэкенд «по учебнику», через неделю всё забывается — было непонятно зачем. Когда вы видите как ваш сайт оживает и параллельно слышите «вот это и есть API», — теория цепляется за реальный момент и остаётся в голове надолго.

Фронтенд vs Бэкенд (на примере Money Tracker)
🖥️

Фронтенд

Что видит пользователь:
• Кнопка "Добавить расход"
• Форма с полями
• Список транзакций
• Красивые цвета

⚙️

Бэкенд

Что делает сервер:
• Сохраняет транзакцию в базу
• Проверяет что сумма > 0
• Возвращает список транзакций
• Удаляет записи

🗄️

База данных

Где хранятся данные:
• Все транзакции
• Суммы и категории
• Даты операций
• Навсегда в облаке

Аналогия "Ресторан": Фронтенд = зал ресторана (красиво), Бэкенд = кухня (готовит), База данных = склад (хранит). Подробнее в глоссарии →

Это структура данных, которую мы создадим в Supabase в уроке 5. Пока просто запомните — всё просто!
Как всё работает вместе

Путь данных когда вы добавляете расход:

Архитектура Money Tracker 
1. Вы нажимаете "Добавить расход 350р на такси"
                    ↓
2. Фронтенд (React) вызывает Server Action в Next.js
                    ↓
3. Server Action получает данные и проверяет их
                    ↓
4. Сохраняет в Supabase (это и есть наша база данных)
                    ↓
5. Supabase отвечает: "Сохранено! ID = 42"
                    ↓
6. Страница автоматически обновляется
                    ↓
7. Вы видите новую транзакцию в списке
Server Action — это новый способ в Next.js 16 писать бэкенд-логику. Раньше нужны были «API Routes» (отдельные файлы для запросов). Сейчас можно прямо в компоненте написать «эта функция работает на сервере» — и Next.js сам разберётся. Подробно — в уроке 6.2 и 6.6.

🚀 Стартуем — превращаем идею в список задач

Сейчас мы сделаем самое важное действие модуля: скормим описание Money Tracker в Task Master. На выходе получим конкретный план — что делать первым, что вторым, какие подзадачи внутри.

В уроке 5.4 мы научились пользоваться Task Master. Теперь применяем по-настоящему.

Шаг 1 — открыть проект из модуля 5

В терминале:

bash
cd money-tracker   # если папки нет — создайте через npx create-next-app@latest

# Проверьте, что Task Master инициализирован
ls .taskmaster

Если папки .taskmaster нет — выполните task-master init (это из урока 5.4).

Шаг 2 — взять готовый PRD

Мы подготовили для вас полный PRD Money Tracker. Скачайте файл и положите его содержимое (от заголовка # Money Tracker — описание проекта и до конца) в файл .taskmaster/docs/prd.txt вашего проекта.

Скачать PRD.md

Кратко — что внутри PRD:

  • Описание — что строим (учёт доходов/расходов с балансом)
  • Стек — Next.js 16, Supabase + @supabase/ssr, Server Actions
  • 5 главных функций — список, баланс, добавить, изменить, удалить
  • Структура БД — таблица transactions с 7 колонками
  • 10 этапов разработки — это станет задачами Task Master

Шаг 3 — Task Master разбивает PRD на задачи

bash
task-master parse-prd .taskmaster/docs/prd.txt

Команда отправит PRD к ИИ на 30–90 секунд (не прерывайте). Когда закончит — посмотрите результат:

bash
task-master list

Что должно получиться

Примерно такая таблица из 8–12 задач:

Шаг 4 — раскрываем сложные задачи на подзадачи

bash
task-master analyze-complexity
task-master expand --all

Теперь, например, задача 5 «Server Action: addTransaction» превратится в 5.1, 5.2, 5.3 — конкретные шажки.

Готово. У вас на руках полный план модуля — в виде конкретных задач, которые знают ваши Cursor и Claude Code (через AGENTS.md из модуля 5). С этого момента каждый следующий урок = одна (или пара связанных) задача из этого списка + разбор «что мы тут вообще делаем».

Связка «задача → урок»

Чтобы было понятно, какая задача в каком уроке закрывается:

Урок Что закрываем из плана Task Master Что объясняем по дороге
6.2 (теория, без задач) API, HTTP-методы, JSON
6.3 (теория, без задач) База данных, таблицы, типы данных
6.4 Задача 1 — Configure Supabase Что такое RLS, ключи, клиент-сервер
6.5 Задача 2 — Create transactions table Колонки, типы данных, первичный ключ
6.6 Задачи 3, 8 — список + GET API Route Server Component vs API Route
6.7 Задачи 4, 5, 6, 7 — BalanceSummary + CRUD Server Actions, zod, revalidatePath
6.8 Задача 9 — тестирование Thunder Client HTTP-коды, отладка API
6.9 Финальная сборка фронта + задача 10 — деплой Server Component + Server Action в реальном UI

Если задачи в вашем Task Master называются по-другому — ничего страшного. ИИ генерирует немного разные формулировки от запуска к запуску. Главное — порядок этапов и темы.
