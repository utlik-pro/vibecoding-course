Что такое PRD и зачем он Task Master

Простыми словами: PRD — это «техзадание самому себе» на проект. Документ, по которому и вы, и ИИ знают, что мы строим, прежде чем начать писать код.

1. Аналогия: PRD как чертёж дома

Представьте, что вы хотите построить дом. Вы можете:

❌ Без чертежа

Приходите к строителям и говорите: «сделайте мне дом». Получаете что-то, но не то. Гараж не там, где удобно. Окна не туда, куда хотели. Переделывать поздно — стены уже стоят.

✅ С чертежом

Сначала рисуете план: «спальня — 15 м², кухня — на восток, два этажа, гараж справа». Строители читают чертёж и делают то, что вы хотели.

PRD (Product Requirements Document — «документ с требованиями к продукту») — это и есть «чертёж» для вашего сайта или приложения. Task Master, Cursor и Claude Code — это ваши «строители». Без чертежа они построят что-то — но это будет не то, что вам нужно.

Главная мысль: 30 минут на PRD сэкономят вам 30 часов переделок. Это самое выгодное вложение времени в проекте.
2. Что произойдёт, если кинуть в Task Master «сделай интернет-магазин»

Давайте посмотрим живой пример. Допустим, вы запускаете Task Master без нормального PRD — просто пишете в prd.txt одну строчку:

плохой PRD
Сделай мне интернет-магазин

Запускаете task-master parse-prd. Что выдаст ИИ?

примерно такие задачи
1. Настроить базу данных (какая БД? какие таблицы?)
2. Создать страницу товаров (что показывать? откуда брать?)
3. Добавить корзину (какие методы оплаты?)
4. Реализовать оплату (Stripe? ЮKassa? CloudPayments?)
5. Подключить доставку (СДЭК? Boxberry? Своя курьерка?)
6. Сделать админку (что должны видеть админы?)
...ещё 20 размытых пунктов

Каждая задача — это огромный знак вопроса. Cursor и Claude Code будут делать что попало, потому что вы им не сказали что хотите. Результат — переделки, путаница, разочарование.

А с нормальным PRD (как мы делали для Money Tracker):

Задачи получаются конкретные:

  • Configure Supabase with @supabase/ssr — потому что в PRD написано «Supabase + ssr»
  • Create transactions table with RLS — потому что в PRD есть структура таблицы
  • Server Action addTransaction with zod — потому что в PRD сказано «Server Actions, zod»

ИИ просто не может ошибиться сильно — у него на руках вся нужная информация.

3. Три части, без которых PRD не работает

Минимально жизнеспособный PRD — это всего три ответа:

Часть Вопрос, на который отвечает Пример
1. Что строим В одной фразе — что это вообще «Сайт, где пользователь записывает доходы и расходы и видит баланс»
2. Из чего строим Технический стек с версиями «Next.js 16, Tailwind 4, Supabase + @supabase/ssr, OpenAI gpt-4o-mini»
3. Какие функции Что пользователь сможет делать «Видеть список транзакций; добавлять; редактировать; удалять; видеть баланс»
Если у вас есть эти три ответа — у вас уже есть рабочий PRD. Можно прогонять через Task Master. В уроке 2 разберём как сделать PRD ещё лучше (структура БД, этапы, исключения).
4. Сколько должно быть в PRD?

Распространённая ошибка — писать диссертацию. Реальность:

  • Меньше 1 страницы — обычно слишком мало. Многие важные решения не приняты, ИИ будет угадывать.
  • 1–2 страницы — оптимально для пет-проекта или MVP. Достаточно деталей, но ничего лишнего.
  • 3–4 страницы — нормально для среднего проекта (как Money Tracker).
  • 5+ страниц — почти всегда плохо. ИИ начинает «теряться», задачи получаются размытыми. Лучше разбить на несколько PRD по фичам.

Сравните: наш PRD Money Tracker — около 2 страниц. Этого хватило на 10 задач + подзадачи.

Антипаттерн: переносить в PRD вообще всё, что когда-то пришло в голову. PRD — это про текущую версию проекта, а не «вижн на 10 лет». Будущие фичи пишите в отдельный файл ideas.md.
Проверка знаний

Что произойдёт, если вы дадите Task Master PRD из одной фразы «сделай мне интернет-магазин»?

Получите идеальный список задач — ИИ умный, всё угадает
Получите размытый список задач без конкретики — потом будет много переделок
Task Master откажется работать, попросит больше деталей
Получится готовый интернет-магазин за 5 минут
